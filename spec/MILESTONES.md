# MILESTONES – אפליקציה לחיפוש ספקים לאחזקת נכסים באוקראינה ובמולדובה

> המסמך מחלק את פיתוח המוצר לאבני דרך, על בסיס [PRD.md](PRD.md), [ARCHITECTURE.md](ARCHITECTURE.md) ו-[DESIGN.md](DESIGN.md). הוא מגדיר **מה** בונים ובאיזה סדר. **איך** בונים מוגדר במסמכים האלה, ואין לסטות מהם.

---

## Development Execution Rules – כללי ביצוע הפיתוח

> **הנחיה מחייבת ל-AI שמבצע את הפיתוח:**
>
> 1. **פתח את ה-Milestones לפי הסדר** שמוגדר במסמך: M1, M2, M3, M4, M5, M6, M7. אסור לדלג על Milestone או לממש חלקים מ-Milestone מאוחר יותר.
> 2. **בסיום כל Milestone, עצור את הפיתוח** והצג למשתמש:
>    - מה הושלם, ואיך אפשר לבדוק את זה (הרצה מקומית, ואחרי הדחיפה גם כתובת ה-Production).
>    - את תוצאות הבדיקה של **כל סעיף** ב-Definition of Done: עבר, לא עבר או לא נבדק, עם הסבר קצר.
>    - פעולות שהמשתמש צריך לבצע בעצמו, אם יש כאלה.
> 3. **אל תתחיל את ה-Milestone הבא בלי אישור מפורש של המשתמש.**
> 4. **הקם חשבונות והגדרות בהדרכה:** את הפעולות שדורשות חשבון או תשלום מבצע המשתמש, לפי הדרכה צעד אחר צעד. זה כולל GitHub, Vercel, OpenAI ו-Supabase. **לעולם אל תבקש מהמשתמש להדביק בשיחה מפתח API, סיסמה או מחרוזת חיבור.** המשתמש מזין אותם ישירות במשתני הסביבה של Vercel.
> 5. **ממש רק את מה שמוגדר במסמכי הפרויקט.** אם חסר פרט מהותי, או שיש סתירה בין המסמכים, עצור ושאל את המשתמש.

### עבודה עם ענפים וסביבות לאורך הפיתוח

| שלב | איפה | Database ומפתחות |
|---|---|---|
| בנייה ובדיקה של כל Milestone | הרצה מקומית במחשב | Development (מקובץ `.env`) |
| "דחוף" (Push ל-`main`) | Production ב-Vercel | Production (ממשתני הסביבה של Vercel) |

יש ענף יחיד, `main`, בלי ענפי עבודה ובלי Preview (ARCHITECTURE.md, ADR-1). כל שינוי במבנה ה-Database רץ ונבדק קודם מקומית על Development. הוא רץ על Production רק בדחיפה, ולפני דחיפה כזו ה-AI עוצר ומבקש אישור מפורש מהמשתמש (ARCHITECTURE.md, סעיף 2.10).

## M1 – תשתית ושלד האפליקציה ✅

**מטרה:** להקים את הפרויקט, את הפריסה האוטומטית ואת השלד החזותי המשותף לכל המסכים, כבסיס שכל ה-Slices הבאים נבנים עליו.

**מה יש לממש:**
- **הקמה בהדרכת המשתמש:**
  - Repository ב-GitHub.
  - חשבון Vercel בתוכנית Pro, וחיבור Git Integration ל-Repository.
- **פרויקט Next.js** (App Router, TypeScript) במבנה התיקיות של ARCHITECTURE.md (סעיף 2.2). כולל `server-only` לתיקיית `/server`, Security Headers, ואזור Functions ‏`fra1`.
- **Design Tokens לפי DESIGN.md:**
  - כל הצבעים כמשתני CSS.
  - הגופנים Italiana ו-Lora.
  - סולם הטקסט, פינות, צללים ומרווחים.
  - סט האייקונים.
- **קטלוג קבוע ב-`/shared/catalog`:** מדינות, ערים ותחומי שירות, בשמות של PRD FR1.2–FR1.3.
- **i18n:** i18next עם קובצי תרגום ru / en / uk לכל טקסטי הממשק שבטבלת הטקסטים של ה-PRD. ברירת המחדל רוסית.
- **Layout משותף:**
  - Header עם ה-Wordmark, הניווט (Поиск / Сохранённые поставщики) ובורר השפות.
  - שני ה-Routes: `/` ו-`/saved`. ב-`/saved` מוצג בשלב הזה רק המצב הריק «Нет сохранённых поставщиков».
- **מסך Поиск (חלק הטופס):**
  - שלושת השדות, כולל התלות בין מדינה לעיר.
  - כפתור Найти מושבת עד שכל השדות מלאים.
  - האיור, לפי ה-Mockups.
- **PWA:** `app/manifest.ts` ואייקונים, להתקנה ב-Android (ARCHITECTURE.md, סעיף 2.3). אין תמיכה ב-iOS (ADR-4).
- **סקריפט Migrations** (`scripts/migrate.mjs`) ופקודת ה-Build ‏`node scripts/migrate.mjs && next build`. הסקריפט מדלג בשקט כשאין `SUPABASE_DB_URL`. זה המצב עד M4.

**תוצר מצופה:** אתר שרץ מקומית, ואחרי הדחיפה גם בכתובת Production, שמציג את מסך Поиск המעוצב עם טופס פעיל ואת הניווט בין שני המסכים. אפשר להחליף בו שפה ולהתקין אותו על מסך הבית ב-Android.

**Definition of Done:**
- [ ] האפליקציה רצה מקומית. Push ל-`main` מפרסם ל-Production אוטומטית (נבדק אחרי הדחיפה).
- [ ] מסך Поиск תואם ל-Mockups בצבעים, בגופנים, בכותרת העליונה, בטופס ובאיור.
- [ ] בחירת מדינה מסננת את רשימת הערים, והחלפת מדינה מאפסת את העיר. Найти פעיל רק כששלושת השדות מלאים.
- [ ] הממשק נפתח ברוסית. החלפה ל-EN ול-UK משנה את כל הטקסטים, כולל שמות המדינות, הערים והתחומים, ו-`lang` של `<html>` מתעדכן.
- [ ] הניווט עובר בין `/` ל-`/saved`, והפריט הפעיל מסומן.
- [ ] הממשק מוצג בלי גלילה אופקית ברוחב 375px וב-Desktop.
- [ ] ב-Android (Chrome) מוצעת התקנה, ואחרי ההתקנה האתר נפתח במסך מלא (נבדק בכתובת ה-Production אחרי הדחיפה).
- [ ] `npm run build` ו-`npm run lint` עוברים בלי שגיאות.

## M2 – חיפוש ספקים מקצה לקצה ✅

**מטרה:** לממש את יכולת הליבה של המוצר: המשתמש בוחר מדינה, עיר ותחום, ומקבל עד 5 ספקים אמיתיים מהרשת, עם בדיקת תנאי הסף ומקורות.

**מה יש לממש:**
- **הקמה בהדרכת המשתמש:**
  - חשבון OpenAI עם שני Projects, ‏`dev` ו-`prod`, כל אחד עם מפתח API ותקרת הוצאה חודשית (ARCHITECTURE.md, ADR-6).
  - הזנת `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_REASONING_EFFORT` ו-`SEARCH_MAX_TOOL_CALLS`, לפי הטבלה ב-ARCHITECTURE.md (סעיף 2.10): ערכי `dev` בקובץ `.env` המקומי, וערכי `prod` במשתני הסביבה של Vercel בהיקף Production.
- **`/api/search`:**
  - ולידציה מול הקטלוג.
  - קריאה ל-OpenAI Responses API עם הכלי `web_search`, הגבלת `max_tool_calls` ותוצאה מובנית לפי סכמה (`json_schema` עם `strict`), כולל Retry ו-Timeout.
  - כללי העסק: אימות מקורות, הסרת כפילויות, חישוב `meetsAllCriteria`, בחירה ומיון, ו-`fewerThanFive`.
  - רישום שימוש (Tokens וחיפושים) בלוג.
  - הכול לפי ARCHITECTURE.md, סעיפים 2.4 ו-2.6.
- **מסך Результаты поиска** לפי ה-Mockups:
  - שורת החיפוש וכותרת התוצאות עם מספר הספקים.
  - כרטיסי ספקים: צ'יפים לתנאי הסף, שורת עובדות, פרטי קשר פעילים (`tel:`, `mailto:`, קישורים), «Источники (N)» והתג «Соответствует не всем условиям».
  - «Нет данных» בכל שדה חסר.
  - **בלי** כפתור השמירה. הוא נוסף ב-M4.
- **מצבי המסך:**
  - «Идёт поиск…» עם פס התקדמות.
  - «Найдено меньше 5 поставщиков».
  - «Поставщики не найдены».
  - באנר השגיאה עם «Повторить».
  - ביטול בקשה קודמת כשמפעילים חיפוש חדש (`AbortController`).
- **החלפת שפה במסך התוצאות** בלי חיפוש חדש, ושמירה של התוצאות כשעוברים בין המסכים.
- **כלל WAF Rate Limiting** על `/api/search`, בהדרכת המשתמש.

**תוצר מצופה:** בהרצה המקומית, ואחרי הדחיפה גם ב-Production, אפשר לבצע חיפוש אמיתי לכל צירוף של עיר ותחום, ולקבל כרטיסי ספקים מעוצבים עם סטטוס לכל תנאי ועם קישורים למקורות.

**Definition of Done:**
- [ ] חיפוש לפחות ב-3 צירופים שונים, כולל עיר במולדובה, מחזיר תוצאות. אף חיפוש לא מחזיר יותר מ-5 ספקים.
- [ ] ספקים שעומדים בכל התנאים מוצגים לפני ספקים חלקיים. לכל ספק חלקי מוצג התג, ואיזה תנאי לא מתקיים או לא אומת.
- [ ] כל קישור שמוצג ב-«Источники» וליד תנאי הסף נפתח, ושייך לתוצאות החיפוש של אותה בקשה. כלומר, אימות המקורות בשרת פעיל.
- [ ] פרטי הספקים מוצגים בשפת המקור, ושדות חסרים מוצגים כ-«Нет данных».
- [ ] מצבי הטעינה, «פחות מ-5», «לא נמצאו» והשגיאה עם «Повторить» נבדקו. ההודעות נבדקו בשלוש השפות.
- [ ] שינוי שדות והפעלת חיפוש חדש בזמן שחיפוש רץ מציגים רק את תוצאות החיפוש האחרון.
- [ ] קלט שאינו בקטלוג נדחה ב-`400`, וחריגה מכלל ה-Rate Limiting מחזירה `429` (נבדק בכתובת ה-Production אחרי הדחיפה, כי ה-WAF פועל רק ב-Vercel).
- [ ] מפתח ה-API לא מופיע בקוד הלקוח (בדיקה ב-Bundle וב-Network).
- [ ] בלוג רשומים זמן התגובה, כמות ה-Tokens ומספר החיפושים. המשתמש קיבל דיווח על זמן התגובה ועל העלות בפועל של החיפושים שנבדקו.
- [ ] המסך תואם ל-Mockups ב-Desktop ומוצג בעמודה אחת ברוחב 375px.

## M3 – ייצוא ל-Excel ✅

**מטרה:** לאפשר למשתמש לשמור ולשתף את תוצאות החיפוש כקובץ Excel.

**מה יש לממש:**
- **`/api/export`:** ולידציה, ויצירת קובץ xlsx עם ExcelJS:
  - בראש הגיליון, פרמטרי החיפוש ותאריך החיפוש.
  - שורה לכל ספק, עם כל השדות מ-PRD FR3.6.
  - כותרות העמודות ושמות הסטטוסים בשפת הממשק.
  - שם הקובץ לפי ARCHITECTURE.md (סעיף 2.7).
- **כפתור «Экспорт в Excel»** במסך התוצאות. הוא מוצג רק כשיש לפחות ספק אחד.
- **הורדה בלקוח:** Web Share API עם קובץ כשהדפדפן תומך, ואחרת הורדה רגילה.

**תוצר מצופה:** בכל חיפוש שמחזיר ספקים אפשר להוריד קובץ Excel עם כל הנתונים, במחשב ובנייד.

**Definition of Done:**
- [ ] הקובץ נפתח ב-Excel. הוא כולל את פרמטרי החיפוש והתאריך, שורה לכל ספק שמוצג, את כל השדות, את הסטטוס של כל תנאי ואת הקישורים למקורות.
- [ ] כשהממשק ב-EN או ב-UK, כותרות העמודות בשפה הזו, ונתוני הספקים נשארים בשפת המקור.
- [ ] כשאין ספקים, הכפתור לא מוצג. בקשה עם רשימה ריקה מחזירה `400`.
- [ ] ההורדה נבדקה במחשב וב-Android, גם כשהאתר מותקן על מסך הבית (ב-Android, בכתובת ה-Production אחרי הדחיפה). אם יש בעיה באחת הפלטפורמות, היא מדווחת למשתמש.

## M4 – ספקים שמורים ✅

**מטרה:** לממש את היכולת שמבוססת על מסד הנתונים: שמירת ספקים מהתוצאות, רשימה משותפת, עדכון סטטוס והערה, ומחיקה. הכול נשמר באופן קבוע.

**מה יש לממש:**
- **הקמת שתי סביבות Supabase, בהדרכת המשתמש צעד אחר צעד** (ARCHITECTURE.md, סעיף 2.10):
  1. **Organization אחד בתוכנית Free** לשני הפרויקטים (פרויקט לימודי, ARCHITECTURE.md ADR-8).
  2. **שני פרויקטים נפרדים בתוכו**, שניהם באזור `eu-central-1`: `suppliers-dev` (Development) ו-`suppliers-prod` (Production).
  3. **בכל אחד משני הפרויקטים** מגדירים את ההגדרות שלא עוברות ב-Migrations:
     - יוצרים Secret Key.
     - מכבים את "Allow new users to sign up".
     - מעתיקים את מחרוזת ה-Session Pooler.
  4. **מזינים** את `SUPABASE_URL`, `SUPABASE_SECRET_KEY` ו-`SUPABASE_DB_URL`:
     - ערכי ה-Development בקובץ `.env` המקומי בלבד.
     - ערכי ה-Production ב-Vercel, בהיקף Production בלבד.
  5. **בודקים** שבמחשב המקומי יש רק את ערכי ה-Development.
- **Migration ראשונה** ב-`supabase/migrations`:
  - הטבלה `saved_suppliers`, עם כל העמודות, אילוצי ה-`check`, שני אילוצי הייחודיות והאינדקס.
  - Trigger ל-`updated_at`.
  - הפעלת RLS בלי Policies.
- **`/server/db`, ו-`/api/saved-suppliers`** עם GET, POST, PATCH ו-DELETE, כולל `409` לכפילות ו-`404` לספק שלא קיים (ARCHITECTURE.md, סעיף 2.7).
- **סימון `savedId`** בתשובת `/api/search`, בלי לשבור את החיפוש כשה-Database לא זמין.
- **מסך התוצאות:** כפתור «Сохранить» בכל כרטיס, שמתחלף ל-«Сохранено».
- **מסך Сохранённые поставщики** לפי ה-Mockups:
  - שורת סינון של מדינה, עיר ותחום שירות, שממולאת מראש מהבחירה בחיפוש. מוצגים רק הספקים של העיר והתחום שנבחרו (PRD FR7.3, ARCHITECTURE.md ADR-7).
  - רשימה ממוינת מהחדש לישן, עם «Всего: N».
  - כפתור «Экспорт в Excel» לרשימה של העיר והתחום שנבחרו, כולל סטטוס, הערה ותאריך שמירה (PRD FR7.10, ARCHITECTURE.md ADR-9). נוסף אחרי אישור M4.
  - כרטיס עם אזור פרטים ואזור עריכה.
  - שדה סטטוס עם ארבעת הסטטוסים וצ'יפים צבעוניים.
  - הערה עם מונה תווים ו-«Сохранить заметку».
  - «Удалить» עם חלון האישור.
  - מצב ריק, הבקשה «Выберите город и вид услуги», והודעת השגיאה «Не удалось сохранить изменения. Попробуйте ещё раз.».
- **כלל WAF Rate Limiting** על `/api/saved-suppliers`.

**תוצר מצופה:** בהרצה המקומית, שמחוברת ל-Database של ה-Development, אפשר לשמור ספקים מהתוצאות, לראות אותם ברשימה המשותפת לפי עיר ותחום, לעדכן להם סטטוס והערה ולמחוק אותם. כל השינויים נשארים אחרי ריענון.

**Definition of Done:**

## M5 – עלייה ל-Production והכנה להדגמה ✅

**מטרה:** לוודא שהמערכת המלאה עובדת בסביבה החיה, ולהכין הדגמה אמינה להגשה המקדימה.

**מה יש לממש:**
- **בדיקה מקיפה בהרצה המקומית ובכתובת ה-Production:** כל ה-Flows ב-PRD ומקרי הקצה שבו, בשלוש השפות, ב-Desktop וברוחב 375px.
- **בדיקת מוכנות של ה-Production**, בהדרכת המשתמש:
  - משתני הסביבה של Production מוגדרים: מפתח OpenAI של ה-Project ‏`prod`, ערכי Supabase של Production ושאר ההגדרות.
  - תקרת הוצאה מוגדרת ב-Project ‏`prod` של OpenAI.
  - כללי ה-WAF פעילים.
  - פרויקט `suppliers-prod` ב-Supabase פעיל ולא מושהה. בתוכנית Free הוא מושהה אחרי שבוע בלי שימוש (ARCHITECTURE.md, ADR-8), ולכן בודקים זאת גם בבוקר ההדגמה.
- **אם נוספו Migrations חדשות מאז M4:** אישור מפורש של המשתמש לפני הדחיפה. ה-Production Build מריץ קודם את ה-Migrations על פרויקט ה-Production, ורק אחר כך מפרסם את הקוד (ARCHITECTURE.md, סעיף 2.10).
- **בדיקת Smoke** בכתובת ה-Production.
- **הכנה וחזרה על הדגמת ההגשה המקדימה**, בכתובת ה-Production:
  - **נתוני הדגמה:** שמירה מראש של כמה ספקים אמיתיים מחיפושים שבוצעו, בסטטוסים שונים ועם הערות. כך אפשר להדגים צפייה, עדכון ומחיקה גם אם החיפוש החי איטי או נכשל.
  - **תסריט הדגמה קצר** (`DEMO.md` ב-Repository), לפי סעיף 5 בדרישות ההגשה:
    1. הצגת הרעיון: מטרה, בעיה וקהל יעד (PRD, סעיפים 1–2).
    2. הדגמה של 3–5 יכולות ליבה: חיפוש, שמירה, עדכון סטטוס והערה, מחיקה וייצוא.
    3. הוכחת שמירה: הצגת השורה בטבלה `saved_suppliers` ב-Dashboard של Supabase לפני ריענון הדף ואחריו.
    4. האוטומציה המתוכננת (PRD, סעיף 6ב).
    5. תכנון ההמשך (PRD, סעיף 6ג).
  - **חזרה מלאה אחת** על התסריט מתחילתו ועד סופו, עם מדידת זמן החיפוש בפועל.

**תוצר מצופה:** המוצר המלא, כלומר חיפוש, ייצוא וספקים שמורים, פועל בכתובת ה-Production, מחובר ל-Database של ה-Production, ומוכן לשימוש עובדי החברה ולהדגמה בהגשה המקדימה.

## M7 – התחברות עם Google ורשימה אישית

**מטרה:** כל משתמש מתחבר עם חשבון Google, והספקים השמורים, הסטטוסים וההערות שלו גלויים רק לו (PRD F6, Flow 6, FR7.1–FR7.3, FR7.8; ARCHITECTURE.md ADR-12).

**מה יש לממש:**
- **הגדרות חשבונות, בהדרכת המשתמשת צעד אחר צעד** (ARCHITECTURE.md, סעיף 2.10, "הגדרות שלא עוברות ב-Migrations"):
  1. **Google Cloud:** פרויקט, OAuth consent screen מסוג External עם ההרשאות הבסיסיות בלבד, במצב Published, ו-OAuth Client מסוג Web application עם כתובות ה-Callback של שני פרויקטי Supabase.
  2. **בכל אחד משני פרויקטי Supabase:** הפעלת הספק Google עם ה-Client ID וה-Client Secret, כיבוי הספק Email, והגדרת ה-Site URL וה-Redirect URLs.
  3. **`SUPABASE_PUBLISHABLE_KEY`:** נוסף ל-`.env.example`. המשתמשת מזינה את ערך ה-Development ב-`.env`, ואת ערך ה-Production ב-Vercel.
- **Migration חדשה:** מחיקת הספקים השמורים הקיימים, הוספת `user_id` עם `references auth.users(id) on delete cascade`, והחלפת אילוצי הייחודיות והאינדקס כך שיכללו את `user_id` (ARCHITECTURE.md, סעיף 2.5).
- **`/server/auth`, `proxy.ts`, מסך `/login` וה-Route Handlers של `/auth/*`** (ARCHITECTURE.md, סעיפים 2.3 ו-2.7).
- **כל ה-Route Handlers של `/api`:** זיהוי המשתמש ו-`401` בלעדיו. כל הפעולות על ספקים שמורים, כולל הייצוא, מסוננות לפי המשתמש.
- **לקוח:** אזור המשתמש בכותרת העליונה (מייל ו-«Выйти»), מעבר ל-`/login` בתשובת `401`, ומחיקת זיכרון החיפוש ב-`sessionStorage` ביציאה.
- **מסך ההתחברות** לפי DESIGN.md סעיף 1.0, עם הטקסטים בשלוש השפות מ-PRD.
- **עדכון `DEMO.md`:** שלב ההתחברות בהדגמה, והסבר שכל משתמש רואה רק את הרשימה שלו.

**תוצר מצופה:** בהרצה המקומית, אי אפשר להשתמש באפליקציה בלי להתחבר. אחרי התחברות עם Google, כל משתמש רואה רק את הספקים השמורים שלו.

**Definition of Done:**
- [ ] ההגדרות ב-Google Cloud ובשני פרויקטי Supabase הושלמו, ו-`SUPABASE_PUBLISHABLE_KEY` מוגדר ב-`.env` וב-Vercel. אין מפתח Supabase בקוד הלקוח.
- [ ] **ה-Migration רצה על Development**, והספקים השמורים הקיימים שם נמחקו. היא תרוץ על Production רק בדחיפה של M7, ולפני הדחיפה ה-AI מציין במפורש שהיא **תמחק את כל הספקים השמורים ב-Production**, ומבקש אישור.
- [ ] משתמש לא מחובר שפותח כל דף מועבר למסך ההתחברות, ואחרי ההתחברות חוזר לדף שביקש.
